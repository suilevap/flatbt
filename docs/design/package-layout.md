# Package layout

Two crates in one workspace:

```text
flatbt-bevy ---> flatbt        (no dependencies)
     |
     +---> bevy_app, bevy_ecs, bevy_time 0.19
```

## Ownership

| Location | Responsibility |
| --- | --- |
| `src/lib.rs` | Root re-exports |
| `src/prelude.rs` | Tree authoring imports |
| `src/runtime/` | BtNode, NodeResult, EntryMode, BtState, update, update_slot, diagnostics |
| `src/composition/` | Static dispatch, custom controls, seq, select, leaf, check, guard |
| `src/params.rs` | Parameter shapes and reborrowing |
| `build.rs` | Tuple states, parameter tuples, child indices |
| `src/nodes/action/` | Lifecycle and cancellation adapters |
| `src/nodes/choose.rs` | Choice policy and `choose!` |
| `src/scope/` | Owned locals, parameter bindings, `scope!` |
| `crates/flatbt-bevy/` | Tree resource, agent component, tick plugin |
| `examples/`, `tests/` | Application examples, test helpers, public API tests |

`nodes` and `scope` use only public core APIs and do not depend on each other.
Application-specific and test nodes stay outside the library.

## When to split a crate

A crate is a unit of dependencies and of release: it is published, versioned and
depended on as a whole. Split one off only for a dependency or a release cadence
the rest does not share. `flatbt-bevy` qualifies on both: it pulls in Bevy, and
exposes Bevy types, so each Bevy upgrade is a breaking release of it alone.

Everything else is a module of `flatbt`. Code without dependencies gets no Cargo
feature either: generic code that is not used is never instantiated, macros cost
nothing until invoked, and each feature would double the combinations to test.

## Dependencies

```toml
[dependencies]
flatbt = { path = "../FlatBT" }
flatbt-bevy = { path = "../FlatBT/crates/flatbt-bevy" } # for Bevy
```

`flatbt_bevy::prelude` re-exports `flatbt::prelude`, so a Bevy game needs one
import.

## Macros

Only `flatbt` reads `FLATBT_MAX_CHILDREN` and `FLATBT_MAX_PARAMS`. A hidden
macro generated by `build.rs` passes the child indices to `choose!`. Exported
macros use `$crate` paths, so they keep working when a consumer renames the
dependency.
